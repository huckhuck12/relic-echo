# 游戏优化清单

更新：2026-11-02；基线版本：0.11.2。按优先级推进，每项以真机结果更新状态。

## 当前事实

- iPhone Air 微信真机曾在怪物较多时降到二十多帧。
- 后续真机性能面板截图显示 202 怪物、206 弹道时仅约 13 FPS，平均帧间隔 75.0 ms；具体数据和分析见下方“真机截图记录”。截图未显示游戏版本，不能默认已经运行最新体验版。
- 用户报告游玩中整个微信退出，当时怪物不算多。根因未确认，不能直接归因为怪物数量或音频泄漏。
- 用户此前报告选卡、怪潮提示和飘字期间摇杆失效，选卡后只能操作固定底盘。
- 0.11.1 已修复触点连续性和装饰节点命中，0.11.2 已补音频回收与本地诊断；均通过模拟环境回归，仍待真机验收。

## 已落地的措施与边界

- **0.11.1 输入修复：**奖励期间保留仍按住的左指，最后一张卡领取后恢复方向；忽略其他手指产生的合成 mouseout；场景和池化飘字不参与触摸命中。失焦、抬指和菜单仍释放输入。
- **0.11.1 渲染优化：**微信引擎渲染像素比上限为 2，缓存静态地面命令，按怪物状态复用有界的形状数据。
- **0.11.2 音频生命周期：**最多同时连接 8 组音效节点，结束、失败和切后台时回收；原生 ended 回调缺失时在后续播放按音频时钟回收。此项尚未证明是闪退根因。
- **0.11.2 排查工具：**启动前注册脚本错误、未处理拒绝及内存告警回调，每 10 秒保存摘要，保留本次与上次运行。暂停菜单可复制诊断；系统/原生终止可能没有回调，Laya 资源计数不等于进程总内存。
- **验证现状：**200 项自动测试、H5 与微信真实引擎配合模拟 SDK 的回归通过；这些结果不能代替 iPhone 原生运行验收。

## 已有压测证据

### 真机截图记录（2026-11-02）

来源：用户提供的微信小游戏真机性能面板截图；沿用当前 iPhone Air 测试上下文，截图本身未显示机型、游戏版本、微信/系统版本、画质及热机时长，尚待补齐。

| 指标 | 截图读数 |
|---|---|
| FPS / 平均帧间隔 | 13 FPS / 75.0 ms |
| P95 / 最慢帧 | 81.0 / 82.0 ms |
| 游戏更新 / 绘图指令 | 14.2 / 3.7 ms |
| 怪物 / 弹道 / 掉落 / 效果 | 202 / 206 / 103 / 13 |

采样平均值已严重超出 60 FPS 的 16.67 ms 预算。面板中的更新与绘图指令均值合计约 17.9 ms，与 75.0 ms 帧间隔存在约 57.1 ms 的未覆盖部分；这些均值不等于同一帧的完整 CPU/GPU 时间线，差值只能用于确定下一步采样方向，不能视为实测 GPU 耗时。

`GameLoop` 使用 1/60 秒固定步、每帧最多追赶 6 步；面板更新耗时汇总本帧所有模拟步，不能把 14.2 ms 当成单步耗时。在约 75 ms 帧间隔下可能出现多步追赶，实际步数还受停顿和暂停影响，需要单独记录。

该截图证明了高负载下的性能问题，尚不能解释此前怪物不多时整个微信退出的根因。下一步优先补齐耗时拆分，并用相近实体数量复测；普通怪贴图化作为随后优先对照的渲染方案。

### 浏览器模拟压测

桌面浏览器模拟微信 SDK，240 怪物、208 初始弹道、170 掉落的同轮对比：地面缓存使引擎绘制均值从约 8.66 ms 降到 6.75 ms；给每个怪物单独开启 normal 缓存反而升到约 11.33 ms，因此没有采用怪物逐个缓存。

这些数字只支持相应方案在该测试环境下的取舍，不能据此断言 iPhone 已达到 60 FPS，也不能排除原生资源问题。复现命令：

```powershell
npm run build
npm run build:wechat
node scripts/check-mobile-browser.mjs --wechat --stress
```

## 执行顺序

先完成闪退排查、摇杆真机复验和性能基线，再按实际瓶颈推进渲染或分配优化，之后集中处理视觉统一。每项记录测试设备、微信/系统版本、游戏版本、画质、复现场景和前后数据；无收益或引入回归的方案撤回。
